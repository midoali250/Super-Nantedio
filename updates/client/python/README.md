# Signed update primitives (experimental)

This is not yet an integrated updater or a distribution service. A client must pin a real Ed25519 public key, the expected product/platform, and an explicit set of HTTPS origins. The server signs the exact UTF-8 JSON payload bytes; an envelope contains base64 `payload` and `signature`. The payload has only `schema_version`, `product`, `platform`, `version_code`, `size_bytes`, `sha256`, and `url`. A greater integer version is mandatory. Both the original URL and every redirect must be allowlisted.

Only after a valid Ed25519 signature, identity and version check may `download_verified` be called with that verified result. It streams into a temporary sibling, checks size and SHA-256, and atomically renames. These primitives never install or execute a downloaded file. A frontend must obtain explicit user approval, present progress/errors, reverify before installation, and honor platform installation/signing requirements (including Android confirmation). Do not embed GitHub tokens or signing private keys in clients. No production key, URL, hosting service or installer is included. Test keys are generated inside tests and not used for production.

A hash identifies the update bytes but does not authenticate the publisher on its own. Prevent rollback with a persisted trusted version and ensure trust-key rotation and release process are designed before production use. URL allowlisting protects redirects but does not itself defend against a malicious compromised allowed server; signed payloads remain required. Integrate and security-review separately for Android and each desktop platform.
