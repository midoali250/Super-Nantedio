# Super Mario Bros. (World) — desktop

Portable Windows x64 EXE, Linux x86-64 AppImage, macOS Apple Silicon app. Fullscreen starts by default; F11 toggles it. The default Fill mode displays the complete NES image over the whole monitor without cropping, stretching it to the screen ratio. Video settings also offer original 4:3 Fit mode with bars and no distortion, plus Sharp nearest-neighbor or Smooth interpolation. 4K output scales 256×240 NES graphics; it cannot add genuine 4K or 3D detail.

Click the gear at the upper right, or F1/Escape, for the menu. Arrow keys + Enter and mouse work in the menu; gamepad D-pad/button 0 navigate/select, button 1 goes back, button 9 opens it. Controls settings have separate Keyboard, Gamepad and Mouse columns; choose a cell to capture a keyboard key, mouse button, controller button, axis or D-pad. Remapping one device doesn't erase the others. Escape cancels capture. Controller hotplug is supported. The default keyboard mappings are arrows to move, A repeated small jumps, S big jump, Z single fire, X repeated fire, Enter start, right Shift select. Gamepad buttons 0–3 map to these four actions. Cheats are separately toggled in the menu, and settings persist.

The emulator captures `autosave.state` approximately every five seconds during gameplay and when exiting; disk writes run in a background worker (exit waits briefly for the last write); on startup it resumes that state. Manual save and load are in the menu. Settings and state are saved in the user's BitVaultEngine/MarioWorld configuration folder (Windows APPDATA; Linux XDG_CONFIG_HOME or ~/.config; macOS ~/Library/Application Support). An interrupted crash can lose up to the time since the last autosave; old v1.0 did not have save states. No cloud sync.

Updates are optional: Check for updates, then Download update from the menu. They download to Downloads, validate the catalog's size and SHA-256 and are not run automatically; install/run manually. Future publications must update the desktop catalog with each artifact URL, version, size and digest. Historical release files are in the top-level `RELEASE-ARCHIVE` folder, separated by platform/version, and GitHub Releases.

Each OS contains a packaged-app smoke-test tool. GitHub Actions tests actual ROM/core, state serialization/restore, 4K-size scaling, simulated keyboard/mouse/gamepad, repeat inputs and UI navigation/remapping. No physical controller, screen, audio or full-game test was performed. Windows/macOS builds are unsigned and may trigger security warnings; macOS is Apple Silicon only. AppImage requires compatible glibc and graphics/audio drivers.

Runtime dependencies: pygame 2.6.1 wheels (including SDL components) in `desktop/vendor`, Python and those components bundled by PyInstaller; FCEUmm sources in the existing game tree. Build-time tools are obtained by GitHub Actions. See licenses inside wheels and emulator sources; redistribution of ROMs may require rights.

Performance: snapshots are serialized on the emulator thread and disk writes happen in the background, the 4K scale buffer is reused, audio queue is bounded, and emulation uses the core frame rate with bounded catch-up. No software can guarantee zero stutter on every device: slow drivers, CPU, display or disk may still affect performance. The performance workflow benchmarks 4K scaling and save costs on GitHub-hosted machines.

Update alerts: while the desktop game is running it checks at launch and about every five minutes. A new version shows a 15-second in-game banner and a persistent red mark on the gear; clicking the banner opens the update menu. It also attempts native Linux (notify-send or gdbus), macOS (osascript) and Windows notifications. System notifications depend on desktop notification permissions, tools/session and Windows PowerShell notification settings; Windows notifications may be attributed to PowerShell; the in-game alert works independently. No background checks occur after the game is closed. Android has its own existing per-game updater, Android notification permissions and OS-controlled schedules. An update is announced on platforms for which a new package has actually been published.
